# SHE CARE — UX & Performance Review → Codebase Evidence Report
 
> **Date:** 2026-08-17
> **Input:** Third-party UX/performance review (screen-recording based) of the SheCare mobile app.
> **Scope:** Every observed symptom mapped to concrete evidence in `/workspace/mobile` (file:line) with root cause + fix + priority.
> **Verification note:** The recording cannot prove CPU/RAM/FPS/network/battery numbers — those need profiling. Where a symptom's *exact duration* depends on runtime (backend latency, device), this report states the measurable code-level cause and the profiling step needed to confirm.
 
---
 
## Executive Summary
 
Every symptom in the review traces back to **one of five root causes** in the codebase:
 
1. **Queries with no `staleTime` (default 0) + no server cache warm → refetch every visit** → "screens reload", "Videos blank 8s", "repeated screen loading". (`useContents`, all 4 diary queries, `getJournalEntry`, safety queries.)
2. **Loading UI is a bare `ActivityIndicator` on an empty background** — no skeleton, no content, no hint text → "blank screens", "app looks frozen", "spinners too subtle". A fully-featured `Loader` component exists but is **never used**.
3. **`VideoLibraryScreen`'s "For You" mode has no skeleton while loading** (skeleton is gated on `!forYou`) → genuinely blank list during the 8s wait.
4. **No lazy loading, no React Query pre-warm, no `persistQueryClient`** → heavy startup + first-paint waits on network → "inconsistent navigation", "app heavily dependent on async loading", "cached data not visible immediately".
5. **Keyboard handling is disabled on Android** (`KeyboardAvoidingWrapper` sets `behavior: undefined` off-iOS) → the journal screen gets squashed by `adjustResize` → "significant layout compression".
 
The UX/visual issues (density, small controls, color-only phase encoding, floating Luna overlap, weak text hierarchy) are also confirmed in code and are largely **low-cost theme/component fixes**.

## PART 1 — 🔴 CRITICAL: Long screen-loading times & blank screens
 
### 1.1 Videos screen blank/loading ~8+ seconds
 
**Root cause (three compounding causes):**
1. **No skeleton in "For You" mode.** The skeleton gate is `if (isLoading && !forYou)` (`VideoLibraryScreen.tsx:71`). When `forYou === true` (toggle at `:100`), this is skipped and the screen falls through to the `FlatList` with `effectiveGeneral ?? []` = **empty data** (`:69,161`) → a blank list area during the whole load.
2. **No cache / no staleTime on the content query.** `useContents({ limit: 100 })` (`useVideoRecommendations.ts:45-48`) → `useQuery` in `nurse_content.ts:19-24` has **no `staleTime`** → default 0 → network refetch on **every mount/focus**.
3. **100-item payload rendered through an unoptimized FlatList** (zero perf props, inline `renderItem`, `RN Image` thumbnails) — `VideoLibraryScreen.tsx:161-176,284,338` → once data arrives, rendering 100 cards is itself slow on mid-range devices.
 
**Fixes:**
- Show the skeleton (or a proper `EmptyState` + spinner) in BOTH modes: remove the `&& !forYou` gate (`VideoLibraryScreen.tsx:71`).
- Add `staleTime` (10+ min) + `placeholderData`/initial-data to `useContents` (`nurse_content.ts:19-24`).
- Apply the 4 standard FlatList perf props + memoize `ContentCard` + swap to `expo-image` (`VideoLibraryScreen.tsx:161-176,330,338`).
 
### 1.2 Journal Entry blank ~20+ seconds in one transition
 
**Root cause:**
- Loading UI is a **bare spinner on an empty background**: `if (entryLoading) { <ActivityIndicator size="large"/> }` (`JournalEntryScreen.tsx:174-178`). Nothing else renders — no skeleton, no title, no "Loading entry…" text → looks blank/frozen.
- The single-entry query `useQuery({ key: ['wellness','journal',id], queryFn: getJournalEntry })` (`:63-66`) has **no `staleTime`** → refetches every visit; on a slow backend this is a full network round-trip (plus default retry logic adds up to 2 retries on failure).
- The screen is **statically imported** (`FeatureStacks.tsx:12`) so it is parsed at startup — the delay is network + render, not first-parse.
- While the reviewer saw ~20s, the *measured* duration depends on backend latency for `GET /wellness/journal/{id}`; the code guarantees a **blank-looking wait** for as long as it takes.
 
**Fixes:**
- Render a **skeleton editor** (title + body lines) instead of a spinner while `entryLoading` (`JournalEntryScreen.tsx:174`).
- Add `staleTime` + `placeholderData` (from the already-cached journal list item) to `:63-66`.
- Show "Draft restored" / "Loading draft…" hints so the state is legible.
 
### 1.3 Daily Log shows a noticeable blank/loading period
 
**Root cause:**
- Loading state is a bare `ActivityIndicator size="large"` on empty background (`DailyLogScreen.tsx:176-177`).
- Data fetch does **three sequential async steps per month switch**: network `getDays` → SQLite `upsertMany` write → `getByRange` read (`cycle.ts:524-540`), all awaited inside the query before anything renders. The SQLite write is an N-statement loop (`BaseLocalService.ts:38-56`) with no transaction → the slowest part.
- No `initialData`/cached placeholder — on every month change the spinner replaces the whole list.
 
**Fixes:**
- Keep the previous month's list visible with a `refreshing` indicator while the new month loads (`DailyLogScreen.tsx:176`).
- Render skeleton day-cards instead of a spinner.
- Batch the SQLite write via `withTransactionAsync` (`cycle.ts:531`).
 
### 1.4 Blank screens during navigation (general)
 
**Root cause:** The dominant pattern is `if (isLoading) return <bare ActivityIndicator/>` on an empty background — seen in `JournalEntryScreen.tsx:174`, `DailyLogScreen.tsx:176`, `JournalListScreen.tsx:109`, `MoodHistoryScreen.tsx:72`, `InsightsScreen.tsx:29`, `BreathingListScreen.tsx:39`. The shared `Loader` component (overlay + accessibility) exists (`ui/Loader.tsx`) but is **imported nowhere** (0 usages). Every screen hand-rolls a slightly different spinner → the "inconsistent loading" problem in PART 4.
 
**Fixes:** Standardize on `Loader fullScreen` (or a shared `ScreenSkeleton`) across all screens; add skeleton shapes for list/content screens; always include a label ("Loading your cycle…").
 
### 1.5 Loading indicators too subtle / app looks frozen
 
**Root cause:**
- Several spinners are `size="small"` or default: `Button.tsx:83` (in-button, no size), `LazyScreen.tsx:16` (`size="small"`), `BreathingExerciseCard.tsx:134` (`size="small"`).
- The "For You" blank path (1.1) shows **no indicator at all** → most frozen-looking moment.
- Full-screen spinners sit on a near-white/near-dark background with no message → low contrast, easy to miss.
 
**Fixes:** Skeleton + message + spinner for every async screen; bump small spinners to `large`; use the shared `Loader` with a label.

## PART 2 — 🔴 CRITICAL: Repeated screen loading & inconsistent navigation
 
### 2.1 Screens that were already visited reload instead of showing cached content
 
**Root cause (measurable):** These queries have **no `staleTime` → refetch on every mount/focus**:
- `useContents` — `nurse_content.ts:19-24` (Videos)
- All diary queries — `queries/diary.ts:8-13,56-61,96-101` (full list, unpaginated, no staleTime, no limit)
- `getJournalEntry` — `JournalEntryScreen.tsx:63-66`
- Safety queries — `queries/safety.ts:176-183` (`staleTime: 0` explicitly)
 
Additionally **`persistQueryClient` is deliberately removed** (`providers.tsx:8`) — the cache is in-memory only, so **every cold start is a full refetch** and previously seen data is gone.
 
**Fixes:**
- Add sensible `staleTime` to the queries above (diary 10 min, nurse_content 10 min, journal entry 10 min).
- Add `placeholderData`/`initialData` from SQLite for the diary/nurse lists so visited screens paint instantly.
- Re-add `persistQueryClient` (SQLite-backed) OR keep SQLite as the warm layer and read it as `initialData` on mount.
 
### 2.2 Navigation feels inconsistent (some screens instant, some slow)
 
**Root cause:**
- Screens backed by cached React Query with `staleTime` open instantly; screens backed by `staleTime: 0` queries or `useEffect`-fetches open with a spinner:
  - `EditHealthScreen.tsx:71-93` fetches via `onboardingService.get()` in a `useEffect` with **local state** (not React Query) → reloads + spinner every visit.
  - Diary screens → statically imported + no cache → slow first open, spinner on every focus.
- No lazy loading anywhere; heavy screens (Diary, Analytics, Journal) are parsed at startup (`FeatureStacks.tsx:5-43`, `AnalyticsStack.tsx:5`) — the `LazyScreen` helper is unused.
 
**Fixes:** Lazy-load heavy stacks; move `EditHealthScreen` fetch to React Query; standardize `staleTime`.

## PART 3 — 🟠 UI / INTERACTION problems
 
### 3.1 High visual density (Calendar & cycle screens)
 
**Root cause:** `CalendarScreen.tsx:314-348` stacks 5 phase-overview cards + 5 legend pills + 42 colored cells + buttons in one ScrollView; each cell has a colored accent + up to 3 dots (`Calendar.tsx:286-287`). `CycleDashboardScreen.tsx` adds backfill cards + phase timeline on top. All driven by a single visual language with no hierarchy scale.
 
**Fix:** Reduce legend pills to icons+text pairs; group phase cards into a single collapsible card; space density via the 4px-grid theme tokens.
 
### 3.2 Several controls are very small (interaction areas)
 
**Root cause:**
- Calendar day cells: `dayCell` height **46 pt** (`Calendar.tsx:275`) × ~51 pt wide on a 360 pt screen — under the 44 pt comfortable target, with sub-cell dots (5×5, `:286`).
- Phase labels & legend pills are small text-only tap targets (`CalendarScreen.tsx:235-259`).
- Several settings rows/icons have small hit areas (`SettingsScreen.tsx:49-86`).
- Only some interactive elements carry `hitSlop` (e.g. `LunaOverlay.tsx:418`).
 
**Fix:** Enforce ≥ 44×44 pt hit areas (add `hitSlop` where layout constrains size); enlarge day cells; increase legend pill height.
 
### 3.3 Heavy dependence on color (accessibility)
 
**Root cause:** Phases are differentiated primarily by **accent color** — `getPhaseAccent()` returns a color per phase (`CalendarScreen.tsx:65`), applied per cell (`:268`). The 5 phase legend pills + cycle stats rely on color coding. Screen-reader labels exist (good — `Calendar.tsx:129-130` has `accessibilityLabel` + `role`), but **sighted color-deficient users** get no non-color cue in the grid itself. `.phaseAccentForDate` passed inline (`CalendarScreen.tsx:268`) also causes the grid rebuild issue.
 
**Fix:** Add a text/icon phase glyph inside cells (e.g. first-letter or a small dot + legend order), keep color as a secondary cue; this also feeds the accessible label already present.
 
### 3.4 Weak text visual hierarchy
 
**Root cause:** Many screens use one text style tier with tiny muted captions — e.g. secondary labels at `fontSize 9` inside the analytics SVG charts (`AnalyticsDashboardScreen.tsx:124,135`), small muted descriptions in calendar/cycle cards, and `variant="caption"` colors `muted` for important info (`VideoLibraryScreen.tsx:175`).
 
**Fix:** Define 3–4 typography tiers in `theme/` (title/body/caption/annotation) and promote secondary info from `caption` to `body` where it is decision-relevant (phase names, next-period dates).
 
### 3.5 Floating elements compete with content
 
**Root cause:**
- Luna overlay is `position: absolute; zIndex: 1000` docked above the tab bar (`LunaOverlay.tsx:454,619-622`) and floats over the bottom of every Home-screen card.
- `FloatingActionButton` is `position: absolute; bottom: -24` (`FloatingActionButton.tsx:75-76`) — overlaps content edge.
 
**Fix:** Reserve a bottom inset / safe-area spacer in `HomeDashboardScreen` and `WellnessHomeScreen` scroll containers so content never sits under the floating dock; make the FAB `bottom` positive and add scroll-offset hiding.

## PART 4 — 🟡 FUNCTIONAL-STATE problems
 
### 4.1 Loading states aren't consistent across screens
 
**Root cause (measurable):** Screens use **different, hand-rolled loading UIs**:
- Bare `ActivityIndicator size="large"`: `JournalEntryScreen.tsx:175`, `DailyLogScreen.tsx:177`, `MoodHistoryScreen.tsx:72`, `InsightsScreen.tsx:29`, `BreathingListScreen.tsx:39`, `JournalListScreen.tsx:109`
- Skeleton rows: `VideoLibraryScreen.tsx:364` (`SkeletonRows`), `Calendar.tsx:237-259`
- Shared `Loader` (`ui/Loader.tsx`) with proper overlay/accessibility — **0 usages**
- Different colors/sizes per screen (some `primary`, some default gray).
 
**Fix:** Standardize on one `ScreenLoader`/`Skeleton` component with consistent color, size, label, and accessibility; replace all 6 bare-spinner call sites.
 
### 4.2 Transitions look like complete screen reconstruction
 
**Root cause:** `HomeDashboardScreen.tsx:137-379` is a single monolithic ScrollView rebuilt on every `cycleDay`/speech-bubble update; `freezeOnBlur` (`MainTabs.tsx:137`) freezes but does not lighten the unfreeze — returning to Home re-evaluates the whole subtree with inline closures (`:151,163,171,201,318,331,364`) and re-renders `AnimatedSection` children. Result: tab switches feel like a full rebuild rather than a slide.
 
**Fix:** Split Home into memoized sections (hero, timeline, bento) with stable props; memoize `AnimatedSection` children; this makes tab return feel like a lightweight swap.
 
### 4.3 Keyboard state compresses the journal layout
 
**Root cause (measured):** `KeyboardAvoidingWrapper` sets `behavior={Platform.OS === 'ios' ? 'padding' : undefined}` and `keyboardVerticalOffset={iOS ? 100 : 0}` (`KeyboardAvoidingWrapper.tsx:13-14`). On **Android**, `behavior` is `undefined` → RN falls back to the OS `adjustResize` (Expo default), which **resizes the whole window**, squashing the `ScrollView` content (`:16-21`) into the visible band — exactly the "substantial compression" observed.
 
**Fix:** Set `behavior="height"` (or `"padding"`) on Android too, add `keyboardVerticalOffset`, and use `keyboardShouldPersistTaps="handled"` (already set); consider `adjustPan` via `app.json` `softwareKeyboardLayoutMode` for editor screens.
 
### 4.4 Long scrolling / content-heavy screens
 
**Root cause:** Many screens stack long vertical ScrollViews: `WellnessHomeScreen.tsx:25` (~9 stacked sections), `AnalyticsDashboardScreen.tsx` (SVG charts + 12-month data), `SettingsScreen.tsx:272` (30 rows), `ProfileHomeScreen.tsx:63` (hero + 7 rows + sections), `PregnancyHomeScreen.tsx:100`, `CalendarScreen.tsx` (calendar + 5 cards). None virtualize or collapse; everything is always mounted.
 
**Fix:** Collapsible sections (`SettingsScreen` groups, phase cards), and for truly long data switch to `FlatList`/`FlashList` (the 12-month analytics list is the main candidate — currently `.map` in ScrollView).

## PART 5 — 🟣 PRODUCTION-READINESS concerns
 
### 5.1 Perceived responsiveness is not production-level
 
**Root cause:** The three P0 causes (bare spinners, no staleTime, blank For-You path) make the app *look* frozen for multi-second windows. Combined with the 42-cell calendar grid rebuild per render (`CalendarScreen.tsx:266,268` → `Calendar.tsx:173`) and the unoptimized lists, even warm navigation can jank.
 
**Fix:** Executing PART 1 + PART 2 fixes resolves the visible "frozen" moments. Measure before/after with the profiler (see 5.5).
 
### 5.2 App is heavily dependent on async data loading during navigation
 
**Root cause:** No `prefetchQuery`/`initialData` anywhere (`providers.tsx:19-36` pre-warms nothing); first Home paint waits on `useCycleCalendar` network (`HomeDashboardScreen.tsx:45`); every un-cached screen shows a spinner.
 
**Fix:** Pre-warm cycle calendar + user prefs during `AppProvider`; hydrate diary/journal/nurse lists from SQLite as `initialData`.
 
### 5.3 Cached/previously displayed data is not consistently visible immediately
 
**Root cause:** In-memory-only cache + `staleTime: 0` on several queries + no `placeholderData` from SQLite → previously seen content is not painted on re-visit.
 
**Fix:** `staleTime` per query + `initialData`/`placeholderData` from SQLite + `persistQueryClient` (or equivalent warm-store read).
 
### 5.4 Loading / error / empty states need stronger differentiation
 
**Root cause (measurable):** 
- Loading: bare spinners (PART 4.1).
- Error: only `VideoLibraryScreen.tsx:85-91` has a proper error `EmptyState` with retry; most screens have **no error branch** (e.g. `JournalEntryScreen`, `DailyLogScreen`, diary screens, `MoodHistoryScreen` only handle loading) → network failure silently renders empty/blank.
- Empty: `EmptyState` component exists but is used inconsistently (VideoLibrary, some lists only).
 
**Fix:** Add a shared `ErrorState` (message + retry) to every async screen; differentiate empty vs loading vs error with distinct visuals.
 
### 5.5 Profiling required (cannot be proven from the recording)
 
The review correctly notes no measurement evidence. To close the loop, profile on a mid-range Android device:
- **JS thread:** React DevTools Profiler — verify render times of `HomeDashboardScreen`, `CalendarScreen`, `VideoLibraryScreen` (target < 16 ms/frame).
- **UI thread:** `react-native-performance` / `perf` capture of scroll FPS on Videos/Diary/Calendar.
- **Network:** RN Studio / proxy — bytes for `GET /cycle/calendar` (full-history bug, §9.1), `useContents` 100 items, diary full-list.
- **Memory:** Flipper/Instruments heap across 20 min of use (target no growth); confirm the `gcTime: 24h` in-memory cache (`providers.tsx:28`) isn't leaking.
- **SQLite:** time `upsertMany` backfill (`BaseLocalService.ts:38-56`) and `useCycleDays` write-through (`cycle.ts:531`).
- **Battery:** background Luna idle loop (`LunaOverlay.tsx:150-161`) while Home tab is open but app backgrounded (needs AppState cancel, §6/8).
